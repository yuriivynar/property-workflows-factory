## Research findings

**Database**
- `supabase/migrations/20261026133459_template_versions.sql` defines the current SELECT policies.
  - `templates_select_admin_or_saved`: `role = 'admin' or current_version is not null`. A vendor passes the second branch and sees saved templates.
  - `template_versions_select_admin_or_current`: admin, or the row is the current version. A vendor passes this too.
- `template_sections_select_admin`, `template_tasks_select_admin` and `template_draft_names_select_admin` (in `20261027222444_template_draft_names.sql`) are already admin-only.
- Only `templates` and `template_versions` therefore leak to a vendor, which is what `tests/db/vendor-closed.test.ts` checks.
- The latest migration is `20261031000000_vendor_run_tasks.sql`. The new file needs a later timestamp, for example `20261101000000_templates_closed_for_vendor.sql`.
- Any other policy or `SECURITY DEFINER` function that reads templates may also be reachable by a vendor. In particular, `launch_run` already refuses vendors with `LAUNCH_NOT_ALLOWED`.

**Domain (`src/lib/templates/domain.ts`)**
- `TemplatePage` is currently `"view" | "edit" | "versions"`.
- `templatePageAccess` returns "ok" for `view` for every role, so a vendor would pass.
- There is no `refusalBackLink`. `TEMPLATE_MESSAGES.backToTemplates` exists, but there is no "Back to runs" text. `LABELS.backToRuns` in `@/lib/runs/messages` may already hold it, so I should check it before adding a duplicate.
- `AppRole` already includes `vendor`, and `currentUser` already returns it.

**Pages that need a refusal**
- `versions/page.tsx` and `edit/page.tsx` already render `Notice` for a refusal, but with a hardcoded `/templates` link.
- `templates/page.tsx` has no access check. It calls `currentUser` and then queries.
- `templates/[id]/page.tsx` has no access check. It queries first and treats "no row" as "Template not found".
- `runs/new/page.tsx` has no role check and uses `getClaims` only. It queries templates directly, so the vendor currently sees the launch form.

**Navigation and sign-in**
- `PageShell` takes `signedIn` and hardcodes the three links.
- `layout.tsx` only calls `getClaims()`, so it has no role. It needs a role lookup, for example `currentUser(supabase)`.
- `login/actions.ts` does `redirect(next)`. `safeNextPath` returns "/" both when `next` is absent and when it is explicitly "/", so the two cannot be told apart.
- `login/page.tsx` only emits the hidden `next` input when it is present in the URL.

## Design

1. **Migration** (one file):
   - Drop and recreate the two policies with explicit roles.
   - `templates`: `role = 'admin' or (role = 'manager' and current_version is not null)`.
   - `template_versions`: `role = 'admin' or (role = 'manager' and exists(... current version ...))`.
   - Leave the four admin-only tables alone, and add no functions.
2. **Domain**:
   - Extend `TemplatePage` with `"list" | "launch"`.
   - Make `templatePageAccess` return `"not-enough-rights"` for a vendor on every page. A manager gets "ok" for list, launch and view. An admin gets "ok" everywhere.
   - Add `refusalBackLink(role)` and a `backToRuns` string.
3. **`src/lib/auth/nav.ts`**: pure `navItems(role)` and `landingPath(role)` as specified in the contract.
4. **Pages**:
   - Add one small shared server component for the refusal, built from `Notice`, `TEMPLATE_MESSAGES.notEnoughRights` and `refusalBackLink(role)`. Every page calls it.
   - Check access right after `currentUser` and before any query, so no template data is requested for a vendor.
   - On `/runs/new`, replace the `getClaims`-only check with `currentUser`.
5. **PageShell**: change the props to `signedIn` plus an optional `role`, and render `navItems(role)`. If there is no role, show the manager/admin set or nothing, whichever matches the current tests. The layout resolves the role once.
6. **Login**: after a successful `signInWithPassword`, if the submitted `next` is empty or "/", read the role and `redirect(landingPath(role))`. If the role lookup fails, fall back to `next`. An explicit `next` other than "/" stays as it is.

## Risks

- **`PageShell` signature change.** Existing DSYS tests may render `PageShell` with only `signedIn`, so `role` must stay optional and the current default must keep the manager/admin links.
- **Manager regression in the policies.** An explicit `manager` branch is required. Writing only `admin or current_version is not null` would keep the vendor leak.
- **Unknown roles.** `current_app_role()` could return null for a profile with no row. Listing roles explicitly gives no rows in that case, which is the safe outcome.
- **Redirect rule.** The login action cannot tell "no next" from "next = /". I'll treat both as "no explicit page". The cost is that a vendor who explicitly asked for "/" lands on `/runs`, which is acceptable.
- **Runs pages unaffected?** `/runs/new` currently depends on `templates` being readable. Closing the policies must not break the vendor's own runs pages or `staff_directory`, so I should grep the vendor run pages for `templates` joins before slice 3.
- **Server actions.** `templates/actions.ts` and `runs/new/actions.ts` check roles before writing. I did not re-read them, and slice 4 should confirm they reject a vendor, since the policies and `launch_run` back them up.
- **Design rules.** Use only `@/components/ui` components and semantic tokens (`npm run check:design`). Texts must match the acceptance criteria exactly.
